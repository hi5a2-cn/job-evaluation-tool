# Jet Constitution

## 产品定位

Jet 在求职者自己浏览招聘平台时，读取他打开的岗位，按他自己的画像判断是否适合，并在之后浏览时提醒他哪些岗位已经判断过，也会在聊天时为他生成沟通建议（由他自己复制使用）。
第一阶段只给项目作者本人在自己的 Mac 上使用；架构从第一天起支持第二阶段让几个朋友加入。

## Core Principles

### I. 主线优先

主线是：用户自己浏览 → 插件读取当前页面 → 入公共岗位库 → 按个人画像判断 → 在页面上提醒 → 沟通辅助 → 反馈。
"沟通辅助"只生成建议，由用户自己复制使用，不自动填入、不自动发送。自动打招呼、自动填入、自动发送仍属外围功能，不进主线（与原则 V 一致）。
任何功能先回答"它服务主线的哪一步"。答不上来的放进 GitHub Issues，不进当前规格。

**理由**：旧版 Jet 在"岗位是公共的还是个人的"这类基础问题还没回答时，就叠加了多用户等功能，
导致数据模型和统计口径至冻结都未收敛（C2、C5）；自动打招呼、状态同步等外围功能的范围
也一直没有定下来（D8）。先把主线做通，才有稳定的基础去判断其他功能值不值得做。
2026-09-26 加入"沟通辅助"：003 在聊天页为用户生成与 HR 沟通的建议，帮用户问出岗位实际情况（记入"HR 实际情况"，成为判断的反馈来源）；它不代替用户操作页面，与原则 V"不自动打招呼、不自动聊天"不冲突。

### II. 数据归属从第一天明确

- **公共岗位库**：所有用户读到的岗位都汇入同一个岗位库。同一个岗位（以平台岗位 ID 为身份）只存一份，
  重复读到时合并：更新内容、保留历史版本。
- 适合和不适合的岗位都进公共岗位库。只在列表页读到、没打开过详情的岗位也进库，并标记"仅列表信息"；列表预判数据存入独立的预判表按用户隔离，不写入判断表。
- **个人数据**：画像、判断结果、查看记录（哪个用户在什么时间、在哪类页面上读到了这个岗位）、收藏、投递、反馈，
  全部按用户隔离，每条记录都有明确的所属用户。
- 不允许出现"没有主人"的个人数据；公共岗位本身不属于任何个人。
- 其他用户看不到"谁看过这个岗位、谁对它做了什么判断"。

**理由**：旧版 Jet 同时存在"岗位属于某个用户（`owner_id`）"和"岗位共享、每人只有私有状态"两套模型，
状态在两张表里各存一份，还留下一批 `owner_id` 为空的老数据，冻结时仍在补救（C2）。
数据归属不清也直接造成了统计口径混乱（C5）。这个决定必须在建表之前做出（D2）。

### III. 插件与本机 Jet 分离

- **浏览器插件**运行在用户自己的 Chrome 里，只负责三件事：读取当前页面已有的岗位数据、发给本机 Jet、在页面上显示提醒。
  插件不做判断，不长期保存个人数据副本（只允许为恢复页面状态使用浏览器关闭即清除的临时缓存），不保存任何平台登录凭据。
- **本机 Jet** 负责岗位库、个人数据、判断和预算，不运行浏览器，不保存任何平台登录凭据。
- 两者之间只通过一个明确的本机接口交换数据：只监听 `127.0.0.1`，只接受已配对插件的请求。
  第一阶段两者都在同一台 Mac 上，但代码边界必须按"以后会分开"来写。

**理由**：旧版 Jet 在运行界面的机器上弹出登录浏览器，部署到没有桌面的 VPS 后，任何用户都看不到这个窗口（D1）；
多个用户又共用同一个浏览器 profile 和同一套平台 Cookie，一个人登录会覆盖另一个人（C3）。
001 的真实验证又发现，由自动化框架启动的浏览器会被 BOSS 登录页拒绝，而隐藏自动化特征属于规避检测，已放弃
（specs/001-boss-search-ingest/research.md §7，见 001-boss-search-ingest 分支（已被 002 取代））。由用户在自己的浏览器里正常登录、正常浏览，Jet 只读结果，
可以从结构上避免登录、profile 和焦点这三类问题。

### IV. 只读，不向招聘平台发起任何请求

- Jet 的任何部分（插件和本机 Jet）都**不向招聘平台发起任何请求**；插件只允许与本机 Jet 接口通信。
- 插件只读取用户当前打开的页面**已经加载**的数据；不导航、不点击、不滚动、不翻页、不打开新页面。
- 插件不替换、不包装页面自己的函数或属性；除了显示提醒，不修改页面内容和行为。
- 不启动、不控制、不自动化任何浏览器。
- 读不到或看不到的信息要如实标注，"不知道"不能显示成"没有"：例如薪资不可见（可能未登录）记为"薪资不可见"，不能记为空薪资。

**理由**：以前连 9222 端口或用户日常 Chrome 会抢焦点、串 Cookie、连错浏览器（B2），
旧版 Jet 新旧两套浏览器机制并存（C3）；参考项目的经验是主动构造接口请求会被识别为异常（001 research.md §1）。
只读用户自己已经打开的页面，平台看到的就只是用户本人的正常浏览。
旧版 Jet 把"浏览器没开"判成"未登录"、界面长期误报（C1、D4），同类错误不能换个形式再出现。

### V. 平台风险控制

- 不自动打招呼、不自动聊天、不自动投递，也不代替用户做任何页面操作。
- 出现验证码或风控页面时，插件什么都不做，由用户按平时的方式处理。
- 不绕过、不屏蔽平台的任何检测机制（验证码、风控、调试工具检测等）。
- 页面结构变化（读不出预期数据）时：明确提示"无法识别"，不把无法识别记成"没有岗位"或"不适合"，
  也不退回读整页文字这类会混入推荐内容、污染数据的降级做法。

**理由**：自动化做到哪一步，决定了账号被封的风险（D8）。
002 实验中，打开浏览器开发者工具会使 BOSS 页面跳到空白页（关闭插件后同样如此），说明平台会主动检测；
Jet 的做法是换一种不依赖开发者工具的读取方式，而不是对抗检测。
平台页面结构迟早会变，读取失败应当被当作正常情况明确报告，而不是静默降级（B1）。

### VI. 耗时任务后台化

- 判断（尤其是大模型调用）在本机 Jet 的后台进行；插件发出岗位后不等待判断完成，页面浏览不受影响。
- 同一用户对同一岗位的判断，同一时间只有一个在进行；重复到达的请求合并处理。
- 打开或刷新插件界面、打开设置页，绝不会启动判断任务。
- 沟通辅助的自动生成不属于判断任务；它由用户在设置中开启、经单独同意、受每日次数上限约束，不违反本原则（2026-09-26）。

**理由**：Streamlit 每次交互都会重跑整个脚本，用户连点"登录"曾拉起多个子进程争抢同一资源，
只能事后补一把文件锁（B3、D7）。任务的并发控制要一开始就和它保护的对象（同一用户的同一岗位）对齐（C3）。

### VII. 成本有上限

- 每一种花钱的调用（大模型等）都有独立的数量上限和预算配置，不与其他数量共用；大模型调用有每日上限，可配置、默认保守。
- 先用规则粗筛，再对候选岗位调用大模型。
- 已判断过的岗位不重复调用大模型；只有岗位内容、画像或判断方式发生变化，并且用户点了"重新判断"或打开了该岗位详情时，才再次调用；不批量重判，不在额度不足时排队到以后执行。
- 允许对"仅列表信息"的岗位做大模型预判，但必须标明是"预判"、不写入判断表（judgements）、不当作正式结论、不影响"已判断不重复调用"规则；预判额度单独设每日上限（按"页"计，默认每天 20 页，可在设置页修改），上限用完当天不再预判、不在额度不足时排队到以后执行。

**理由**：旧版 Jet 把采集上限提到 200 时，分析上限因为共用同一个校验函数也被放到 200，
一次运行可能调用 200 次大模型（B7）。预算和上限需要统一管理的位置（D9）。
改为插件后，用户每打开一次页面都可能触发判断，不设去重和每日上限，费用会随浏览量线性增长。
判断方式升级后，要求逐个手动"重新判断"负担过重（2026-09-25 用户反馈）；用户打开岗位详情本身就是明确的动作，此时更新过时判断，仍然只针对用户正在看的那一个岗位，费用可控。
2026-09-30 允许列表预判：用户希望在列表页快速了解岗位是否值得点开。列表信息不完整，因此预判绝不是正式结论、不进判断表；按页打包一次性预判控制调用次数，配合独立的每日页数上限（默认 20 页），防止浏览列表时费用失控。

### VIII. 测试与数据安全

- 数据目录是可注入的参数，代码中不写死真实数据路径。
- 默认测试不联网、不需要 API Key、不打开真实浏览器、不访问招聘平台；使用保存的页面数据样本。真实环境测试必须显式开启。
- 页面数据样本进仓库前必须去掉个人信息（如招聘者姓名、会话参数）。
- 测试写入真实数据目录即判为失败（自动检查）。
- 个人资料、Cookie、Token、配对密钥、数据库不进 Git。

**理由**：旧版 Jet 的测试曾在真实 `data/runtime` 下留下锁文件和任务目录，数据路径又是写死的，
只能靠 monkeypatch 绕开（B4、A10）。在干净环境里有 15 个测试因缺 API Key 或真实浏览器而失败，
"本机全绿"并不代表换一台机器也全绿（B6）。

### IX. 每个数字都有定义

界面和报告上出现的每一个统计数字，都要在指标定义表里写清：数的是什么、按谁过滤、时间范围。

**理由**：旧版 Jet 同一排数字里有的算全库、有的算个人，推进阶段统计取的是哪一份状态要看数据怎么加载，
搜索过程和任务汇总又是两套口径（C5）。开发前先写指标表（D6）。

### X. 证据与最小改动

- 汇报时区分 FACT / INFERENCE / HYPOTHESIS；没有在真实环境验证过的行为标注 NOT VERIFIED。
- 只改完成当前任务所必需的内容；范围需要扩大时先停下来说明。

**理由**：旧版 Jet 中有多处结论只在假页面或特定本机环境下成立，例如解析测试从未对真实 BOSS 页面跑过（A2），
本机测试依赖 `.env` 和已登录浏览器（B6）；不标注证据等级，就无法区分"已验证"和"看起来能用"。

### XI. 代码组织

- Python 代码全部放在 `jet` 包下，不使用 `integrations`、`job_analysis` 这类通用顶层包名。
- 浏览器插件代码放在仓库的 `extension/` 目录下。
- 不依赖旧的浏览器自动化工具和旧版 Jet；旧代码只能"复制并附带测试"迁入，不能直接引用。

**理由**：旧的浏览器自动化工具和旧版 Jet 都声明了顶层包 `integrations`、`job_analysis`，两份代码已经分叉，
实际导入哪一份取决于从哪个目录启动，而且不会报错（C4、A7）。代码的正本放在哪里必须明确（D5）。

## 附加约束

技术约束（第一阶段）：

- 本机 Jet：Python，SQLite（公共库和个人数据在同一个数据库中，按用户隔离），本机 HTTP 接口只监听 `127.0.0.1`。
- 浏览器插件：Chrome，Manifest V3。用户界面（如画像编辑）放在插件的页面里。
- 只在本机运行，不部署服务器。

## Governance

- 修改本 constitution 需要用户确认，并更新版本号。
- 规格、计划、任务遵循 Spec Kit 流程；长期待办放 GitHub Issues。
- 版本号规则：删除原则或改变原则含义 → 主版本号；新增原则 → 次版本号；措辞修订 → 修订号。
- 每次执行 /speckit-plan，都必须逐条对照本 constitution 做检查。
- 优先级：本 constitution > 规格和计划 > 其他文档；发现冲突时停下来问用户。
