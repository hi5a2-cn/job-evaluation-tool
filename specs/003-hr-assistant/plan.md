# Implementation Plan: HR 沟通助手 + 我的岗位库改版

**Branch**: `003-hr-assistant` | **Date**: 2026-09-26 | **Spec**: [spec.md](spec.md)

**Input**: 唯一需求来源：`specs/003-hr-assistant/spec.md`（基于 `docs/drafts/feature-003-draft.md` 确认稿）；遵循 constitution（`.specify/memory/constitution.md`）；参考 002 插件与本机接口规范。

## Summary

本功能包含两个模块：
1. **HR 沟通助手（P1）**：在 BOSS 聊天页，用户打开 Chrome 侧边栏点击"生成"按钮，由插件读取当前页面已加载的会话信息与最多 30 条非系统消息，发往本机 Jet 服务。本机 Jet 服务结合当前岗位的 Jet 判断结论、HR 实际情况、用户录入的「我的经历素材」（最多 10 条）以及独立的语气规则文件，在服务端执行确定性的纯函数脱敏并计算哈希；在获得用户显式知情同意（首次弹出只读预览）后，单次调用 DeepSeek 大模型（关闭思考模式），生成 2 个语气版本的建议话术（≤ 50 字）及最多 3 个建议问 HR 的问题，供用户手动复制。系统不自动填入输入框、不自动发送；服务端不持久化存储聊天原文与生成建议；用户切换聊天时侧边栏旧结果立即全部清空。
2. **我的岗位库改版（P2，Issue #5）**：重构独立标签页 `myjobs.html`。在每行卡片中直接展示 HR 告知的实际情况（两行自适应截断，可展开查看全文 ≤ 200 字），支持行内就地修改但禁止清空；标签栏最前面新增第 6 个标签「全部岗位」（范围为有状态 ∪ 判断过 ∪ 有 HR 记录），支持叠加「只看有 HR 记录」过滤并联动更新各标签数量；支持在当前视图下通过服务端 SQLite 搜索职位名（包含所有历史版本）、公司名和 HR 记录内容；支持在行内直接修改状态，修改后留在原位不跳动并显示移出标注。

## 已定方向（遵照规范，不得修改）

1. **脱敏、同意、鉴权与调用全部在服务端**：脱敏逻辑、同意记录检查、同意预览组装以及大模型 HTTP 调用全部在本机 Jet 服务中完成；插件只负责在点击生成时读取页面、把原始数据发给本机服务、在侧边栏显示结果；插件端绝对不持有 API Key（FR-009、FR-027）。
2. **"预览里看到的 = 实际发送的"**：服务端脱敏是确定性的纯函数。预览接口返回脱敏后的完整发送文本及其 SHA-256；用户点同意后，插件将同一份读取结果与该哈希一起发给生成接口，服务端重新脱敏并比对哈希，不一致直接拒绝并拦截（400），防止数据被篡改。服务端不落盘保存聊天内容（FR-036）。
3. **单一来源存放**：
   - **我的经历素材**：存放在本机 Jet 服务数据库（新表 `experience_items`，按用户隔离，最多 10 条、每条 ≤ 200 字，无版本记录），设置页通过本机接口读写（FR-028、FR-033）。
   - **发送同意记录**：存放在本机 Jet 服务数据库（新表 `llm_consents`，记录同意时间、撤回时间、同意时的字段版本 `fields_version`），服务端在生成前校验，设置页撤回走本机接口（FR-025、FR-026）。
   - **语气规则文件**：存放在仓库代码树内的单独文本文件（`src/jet/llm/prompts/tone_rules.txt`），服务每次生成时读取该文件，修改规则随代码版本管理且无需重启服务即时生效（FR-034）。
4. **新增 llm_calls 用途与额度控制**：`llm_calls` 表新增用途 `assist`（生成话术），采用 002 的数据库迁移方式升至 `user_version = 5`（迁移前备份 `jet.db.bak-<时间>-v4`）。每日上限由环境变量 `JET_DAILY_ASSIST_LIMIT` 单独配置（默认 50，范围 0–500），计次口径严格符合 spec 指标定义（FR-037、FR-038）。
5. **模型接入**：沿用 002 的 DeepSeek 客户端（`call_once`），关闭思考模式（`thinking: {"type": "disabled"}`），单次调用完成，不采用思考模式复核（FR-018）。
6. **岗位库扩展**：扩展 `GET /v1/my-jobs`，增加 `all_jobs` 过滤、`hr_only` 过滤、`q` 搜索参数与对应计数、总数 N；行内修改 HR 实际情况复用 `PUT /v1/jobs/{id}/hr-note`，插件端严格禁用清空与空白提交（FR-043）；服务端对来自岗位库（`source = myjobs`）的空提交返回 422（第 1 项 A）。
7. **切换发现**：平时 content script（ISOLATED world）在 MutationObserver 触发时只比较聊天顶部区域（`.chat-position-content` 所在的会话顶部）的文字是否变化；变化时由 background 在 MAIN world 只读一次当前会话的 `encryptJobId`，与上次比较，不同才通知侧边栏清空。不读消息区、不滚动、不发网络请求（原则 IV）。依据：实验中会话区的链接时有时无（v0.0.2 为 0 个、v0.0.4 为 1 个），`data-` 属性里没有岗位 ID，岗位 ID 只在 Vue 数据里（MAIN world）。**NOT VERIFIED**：顶部文字是否在每次切换时都变化，需真实页面验证；完整会话与消息仅在点击生成时读取一次（FR-004、FR-005）。用户点'复制'时，插件再读一次当前聊天的岗位 ID（MAIN world 只读），与生成结果绑定的岗位 ID 不一致就拒绝复制，并提示'已切换到新的聊天，请重新生成'。

## Technical Context

**Language/Version**: Python 3.12+（本机 Jet 服务）；原生 JavaScript（ES2022，Chrome 扩展，无构建打包步骤）。

**Primary Dependencies**:
- 后端：FastAPI、uvicorn、httpx（OpenAI 兼容 `/chat/completions` 客户端）、pydantic；
- 插件端：原生 Web API、Chrome Extension Manifest V3 API（`chrome.sidePanel`, `chrome.scripting`, `chrome.storage`, `chrome.runtime`），无第三方外部依赖。

**Storage**: SQLite 3（标准库 `sqlite3`，WAL 模式），单文件数据库，位于可注入的数据目录（默认 `~/Library/Application Support/Jet/jet.db`）。

**Testing**:
- 后端：pytest、FastAPI TestClient、FakeLlmHelper（mock 传输层）、临时隔离数据目录；
- 插件端：Node.js 原生测试运行器 `node --test extension/tests/*.test.js`；
- 原则：默认测试不联网、不需真实 API Key、不启动真实浏览器。

**Target Platform**: macOS（Apple Silicon）本机运行；Chrome 稳定版（MV3，Chrome 114+）。

**Project Type**: 单仓库混合架构（`src/jet/` 本机后台服务 + `extension/` 浏览器扩展）。

**Performance Goals**（目标值，均 NOT VERIFIED）:
- 聊天切换发现：< 10ms 响应，侧边栏立即清空旧内容；
- 本机脱敏与哈希计算（预览接口）：< 50ms 完成；
- 大模型生成话术：10 秒内返回结论（超时配置为 20 秒，超时明确提示失败）；
- 岗位库搜索与列表加载：200 条数据加载及 LIKE 模糊检索在 100ms 内完成。

**Constraints**:
- 严格绑定 `127.0.0.1`，拒绝普通网页跨域调用；
- 插件端绝不持有 DeepSeek API Key；
- 绝对不向招聘平台（zhipin.com）发起任何主动请求；
- 聊天原文与生成建议话术绝对不写入数据库与持久文件（仅存侧边栏内存）；
- 每日生成上限默认 50 次，在 SQLite `BEGIN IMMEDIATE` 事务中进行严格预占。

**Scale/Scope**:
- 单用户本地系统；
- 经历素材最多 10 条（单条 ≤ 200 字）；
- 聊天消息单次最多读取最近 30 条已加载非系统消息；
- 岗位库单次查询返回最多 200 条，提供总匹配数 N。

## 待用户拍板的决定（2026-09-26 已决定）

以下 7 项决定涉及用户日常使用体验或底层兼容性，请审阅：

1. **服务端是否也拒绝岗位库来源的空提交（HR 实际情况修改）** → 用户选 A（2026-09-26）
   - **选项 A（推荐）**：服务端接口 `PUT /v1/jobs/{id}/hr-note` 增加可选字段 `source`（取值 `myjobs` 或 `card`）。当 `source == 'myjobs'` 且提交文本经 `strip()` 为空时，服务端返回 422 错误 `empty_not_allowed` 并提示"清空请到岗位卡片操作"；当 `source == 'card'` 时允许清空（保持 002 语义）。
   - **选项 B**：服务端不作来源校验，仅在插件端岗位库 UI 上做输入校验与按钮禁用；若用户绕过前端调用接口仍然允许清空。
   - **推荐理由**：推荐选项 A。由前后端双重拦截，既能在 UI 端给用户清晰引导，又能防止意外绕过导致岗位库中的重要信息被误删，且不破坏卡片端原有的清空能力。

2. **"姓 + 称呼"去名时复姓（如欧阳、诸葛）怎么处理** → 用户选 A（2026-09-26）
   - **选项 A（推荐）**：服务端维护一个常见 30 个复姓词表（欧阳、上官、诸葛、司马等）。脱敏时若姓名字首匹配复姓，则提取"复姓 + 称呼"（如"欧阳女士"）进行正则剔除；未命中复姓时取名字首字（单字）+ 称呼（如"刘女士"）。
   - **选项 B**：不论姓名几个字，统一只取第一个单字 + 称呼进行过滤（欧阳取"欧女士"）。
   - **选项 C**：不依据结构化姓名，直接用正则全局脱敏聊天中出现的任意"X女士/先生/老师/总"。
   - **推荐理由**：推荐选项 A。复姓在中文中虽属少数但真实存在（如"欧阳老师"），若仅按单字切分会导致"欧阳老师"脱敏不彻底并残留"阳老师"；维护轻量复姓表能精准脱敏且不会像选项 C 那样误伤正文普通词汇。

3. **语气规则文件放仓库还是数据目录** → 用户选 A（2026-09-26）
   - **选项 A（推荐）**：存放在仓库代码树内（`src/jet/llm/prompts/tone_rules.txt`），随 Git 进行版本管理。服务端在每次调用生成时读取该文件内容（支持热加载），修改后无需重启服务即时生效。
   - **选项 B**：存放在用户数据目录内（`~/Library/Application Support/Jet/tone_rules.txt`），首次启动从模板复制，允许用户在本地随意修改。
   - **推荐理由**：推荐选项 A。语气规则属于模型 prompt 算法基准的一部分（FR-034/035），随 Git 版本管理便于回溯、测试对齐和质量评测；同时代码每次调用动态读取文件，用户若需微调只需修改文件即可即时生效，无需重启服务。

4. **数据库迁移与新表规划（新增 llm_calls 用途与新表）** → 用户选 A（2026-09-26）
   - **选项 A（推荐）**：数据库升级至版本 5（`user_version = 5`）。启动时自动备份 `jet.db.bak-<时间>-v4`；在事务中重建 `llm_calls` 表（CHECK 扩展为 `IN ('judge', 'eval', 'assist')`），并新建 `experience_items`（经历素材）与 `llm_consents`（同意记录）表，校验数据完整性与外键后提交。
   - **选项 B**：不升结构版本、不改 `llm_calls` 表的 CHECK 约束，借用既有的 `purpose='judge'`，另外加字段标记。
   - **推荐理由**：推荐选项 A。严格遵循宪法原则 II 与 002 迁移备份规范，表意清晰，统计隔离，数据最安全。

5. **切换发现的读取频率与方式对页面的影响** → 用户选 A（2026-09-26）
   - **选项 A（推荐）**：平时 content script（ISOLATED world）在 MutationObserver 触发时只比较聊天顶部区域（`.chat-position-content` 所在的会话顶部）的文字是否变化；变化时由 background 在 MAIN world 只读一次当前会话的 `encryptJobId`，与上次比较，不同才通知侧边栏清空。不读消息区、不滚动、不发网络请求（原则 IV）。依据：实验中会话区的链接时有时无（v0.0.2 为 0 个、v0.0.4 为 1 个），`data-` 属性里没有岗位 ID，岗位 ID 只在 Vue 数据里（MAIN world）。**NOT VERIFIED**：顶部文字是否在每次切换时都变化，需真实页面验证。仅在用户点击"生成"按钮时，才由 background 执行一次 MAIN world 深度读取已加载的消息与结构化数据。
   - **选项 B**：每次 DOM 变动都通过 `chrome.scripting.executeScript(world: "MAIN")` 深入读取当前会话的全部消息和 Vue 状态。
   - **推荐理由**：推荐选项 A。符合原则 IV（不滚动、不发请求）与 FR-004，日常对 BOSS 页面零性能损耗与零检测风险。
   - **补充（用户决定）**：用户点'复制'时，插件再读一次当前聊天的岗位 ID（MAIN world 只读），与生成结果绑定的岗位 ID 不一致就拒绝复制，并提示'已切换到新的聊天，请重新生成'。切换发现（顶部文字变化触发）在真实页面的可靠性记为待验证项 V8。

6. **HR 沟通助手服务主线的哪一步（constitution 原则 I）** → 用户选 B（2026-09-26）；constitution 已于 2026-09-26 修订为 4.0.0
   - **选项 A（推荐）**：确认它服务"反馈"：它帮用户向 HR 问出岗位实际情况，用户记进"HR 实际情况"，这是判断的反馈来源；在 plan 中写明这一对应关系。
   - **选项 B**：修改 constitution，把"沟通辅助（只生成建议，不自动发送）"明确写进主线或列为允许的外围功能（需更新版本号）。
   - **选项 C**：HR 沟通助手移到 GitHub Issues，003 只做岗位库改版。
   - **推荐理由**：推荐 A。它不自动聊天（符合原则 V），问题清单与 002 的"建议问 HR"、"HR 实际情况"直接相连；如果你认为这是牵强解释，应选 B，而不是悄悄越过原则 I。

7. **读不到"我自己的姓名"（V6）时怎么办** → 用户选 A（2026-09-26）
   - **选项 A（推荐）**：不发送，提示"读不到你的姓名，暂时不能生成"，不调用大模型（宁可不发，也不漏脱敏）。
   - **选项 B**：照常发送，只靠电话 / 微信号 / 邮箱规则脱敏，并在同意预览里提示"未能去掉你的姓名"。
   - **推荐理由**：推荐 A。隐私要求第 2 条要求去掉我自己的姓名；读不到时继续发送就等于没做到。
