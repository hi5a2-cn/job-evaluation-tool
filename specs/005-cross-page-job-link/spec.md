# Feature Specification: 岗位信息跨页面联通（第一批）

**Feature Branch**: `005-cross-page-job-link`

**Created**: 2026-09-29

**Status**: Draft

**Input**: 2026-09-29 用户确认的联通调研结论（搜索列表卡片、右侧详情区、独立职位页、聊天页侧边栏、聊天列表左侧会话条目、我的岗位库 × Jet 判断、粗筛提示、投递状态、HR 记录、聊天进展）中的第 1–4 项。遵循 constitution（`.specify/memory/constitution.md`）。

## 概述

在 BOSS 里，搜索列表、岗位详情和聊天里的同一个岗位本来就是连着的；Jet 的记录目前只在部分位置能看到或修改。本功能补齐四处，让同一个岗位的**投递状态**在各处一致可见、可改，并让聊天中遇到的岗位也能进入岗位库：

1. 聊天页侧边栏显示并能修改当前聊天岗位的投递状态。
2. 搜索列表卡片显示投递状态。
3. 独立职位页点「立即沟通」也自动标记已投递。
4. 聊天中的岗位自动入库（只存页面已显示的三项，不判断）。

所有位置读写的都是本机岗位库里**同一份**状态记录，不新增状态种类。

### 与 constitution 及既有 spec 的关系

- **原则 IV（只读）**：四项都只读取用户当前打开的页面已经加载的数据；第 3 项只被动监听用户**自己**的点击，不阻止、不改变、不代替点击；不向 BOSS 发起任何请求，不改变 BOSS 上的任何状态。
- **原则 VII（先规则、后大模型）**：第 4 项入库的岗位只有职位名和公司名，属于信息不全的岗位，不做规则粗筛、不判断、不调用大模型。
- **修订 003 FR-059 及 User Story 9 验收场景 3**（原规定：不在库时不自动入库）。修订理由：自动入库只在本机保存聊天页上已经显示的岗位 ID、职位名、公司名，**发给外部模型或服务的内容没有任何变化**（不判断、不调 DeepSeek），也不改变岗位状态；好处是 HR 主动发起、我从没点开过的岗位也能记录 HR 实际情况和投递状态。
- **扩展 002 FR-058 与 004 FR-017**：原"点「立即沟通」自动标已投递本期不扩展到独立职位页"，由本功能扩展到独立职位页。

## 已确认的页面事实

- 聊天页当前会话的页面数据中有岗位 ID（`encryptJobId`，与岗位库的岗位 ID 是同一种）、职位名、公司名（003 FACT，现有聊天页读取已在使用）；页面顶部岗位栏也显示完整职位名。
- 聊天页顶部岗位栏有「查看职位」，由用户点击后新开标签页打开独立职位页；独立职位页由 004 读取、入库并按现有规则判断（004 FACT）。
- 独立职位页地址形如 `www.zhipin.com/job_detail/<岗位 ID>.html?…`，其中岗位 ID 与列表、聊天中的一致（003/004 FACT）。
- 独立职位页上「立即沟通」按钮的具体位置**未经探测确认**，实现时须用真实页面验证（见 Assumptions）。
- 搜索列表页右侧详情区的「立即沟通」按钮位置已确认（002 FR-058 FACT）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 聊天时直接看到并修改投递状态 (Priority: P1)

我在 BOSS 聊天页和 HR 沟通时，侧边栏的"当前岗位"卡片除了 Jet 结论和 HR 实际情况，还显示这个岗位的投递状态（收藏 / 已投递 / 不考虑，或未设置），我可以当场点按钮切换或取消。改完后，岗位库、搜索列表右侧详情区和独立职位页看到的都是这个新状态。

**Why this priority**: 投递决定常常就在聊天时做出（例如聊完决定不考虑），现在必须切回列表或岗位库才能改，最常用、改动小、接口现成。

**Independent Test**: 打开一个在库岗位的聊天，侧边栏看到状态按钮；点"不考虑"后刷新岗位库，该岗位状态为"不考虑"；再点一次取消，岗位库里变为未设置。

**Acceptance Scenarios**:

1. **Given** 当前聊天岗位在库且状态为"收藏"，**When** 我打开聊天页侧边栏，**Then** 当前岗位卡片显示状态按钮组，"收藏"处于选中态。
2. **Given** 当前岗位状态为未设置，**When** 我点"已投递"，**Then** 状态保存到本机岗位库，按钮组变为"已投递"选中；保存失败时恢复原选中态并提示失败。
3. **Given** 当前岗位状态为"已投递"，**When** 我再次点"已投递"，**Then** 状态被取消（未设置），与岗位库、详情卡片的取消规则相同。
4. **Given** 我在侧边栏修改了状态，**When** 我切到另一个聊天再切回来，**Then** 侧边栏显示的是修改后的状态。

---

### User Story 2 - 搜索列表卡片上直接看到投递状态 (Priority: P1)

我在 BOSS 搜索列表页浏览时，已经设置过投递状态的岗位卡片上直接显示"已投递""收藏"或"不考虑"标识，我不用点开就知道哪些处理过。

**Why this priority**: 状态数据在列表查询时已经一并取回，只是没显示；显示后能减少重复点开已处理的岗位。

**Independent Test**: 在岗位库把某岗位设为"收藏"、另一个设为"已投递"，打开包含它们的搜索列表页，核对两张卡片分别显示对应标识，未设置状态的卡片没有状态标识。

**Acceptance Scenarios**:

1. **Given** 列表中某岗位状态为"已投递"，**When** 列表页加载完成，**Then** 该卡片显示"已投递"标识，并与该卡片已有的 Jet 结论标识或粗筛提示同时可见、互不遮挡。
2. **Given** 我在右侧详情区把当前岗位状态改为"不考虑"（或点「立即沟通」被自动标记已投递），**When** 修改保存成功，**Then** 同一页面上该岗位卡片的状态标识随之更新，无需刷新页面。
3. **Given** 某岗位没有状态，**When** 列表页加载完成，**Then** 该卡片不显示状态标识。

---

### User Story 3 - 独立职位页点「立即沟通」也自动标记已投递 (Priority: P2)

我从聊天页点「查看职位」或其他途径打开独立职位页，自己点「立即沟通」时，Jet 和在搜索列表页一样，把这个岗位标记为"已投递"，并给我约 8 秒的撤销机会。

**Why this priority**: 搜索列表页已有此行为，独立职位页没有，两处行为不一致；改动小。

**Independent Test**: 打开一个状态未设置的独立职位页，点「立即沟通」，页面出现可撤销提示，岗位库里该岗位变为"已投递"；点撤销后恢复未设置。

**Acceptance Scenarios**:

1. **Given** 独立职位页岗位状态不是"已投递"，**When** 我自己点击文字恰好为"立即沟通"的按钮，**Then** 该岗位状态设为"已投递"，显示约 8 秒的可撤销提示；点撤销恢复点击前的状态。
2. **Given** 按钮文字为"继续沟通"或其他文字，**When** 我点击，**Then** 不做任何标记。
3. **Given** 岗位状态已是"已投递"，**When** 我点「立即沟通」，**Then** 不做任何处理。
4. **Given** 标记失败，**When** 保存返回错误，**Then** 显示"未能自动标记为已投递"，不重试。
5. **Given** 任意情况，**When** 我点击按钮，**Then** Jet 不阻止、不延迟、不改变这次点击，BOSS 的沟通流程照常进行。

---

### User Story 4 - HR 主动找我的岗位也进入岗位库 (Priority: P2)

HR 主动找我聊、我从没在列表或详情里点开过的岗位，我打开这个聊天时，Jet 自动把它记进岗位库（只记页面上已显示的岗位 ID、职位名、公司名）。侧边栏显示这个岗位，提示我"点「查看职位」获取详情并判断"；我当场就能设置投递状态、记录 HR 实际情况。它不会被自动判断，也不花任何费用。

**Why this priority**: 目前这类岗位永远进不了岗位库，HR 透露的实际情况无处记录；这是聊天与岗位库联通的主要断点。

**Independent Test**: 找一个本机岗位库没有的聊天岗位，打开该聊天，侧边栏显示职位名、公司名和提示语；岗位库"全部岗位"里出现该岗位；本机大模型调用记录和每日额度前后不变。

**Acceptance Scenarios**:

1. **Given** 当前聊天岗位不在本机岗位库中，**When** 我打开该聊天，**Then** 该岗位以页面上的岗位 ID、职位名、公司名入库；侧边栏当前岗位卡片显示职位名、公司名、投递状态按钮、HR 实际情况输入区，以及提示"点「查看职位」获取详情并判断"。
2. **Given** 上一条入库完成，**When** 我查看本机判断记录、大模型调用记录和每日额度，**Then** 均无变化；该岗位没有规则粗筛结果，也没有投递状态。
3. **Given** 该岗位入库后，**When** 我打开「我的岗位库」的"全部岗位"，**Then** 能看到该岗位（标明尚未判断），可以就地设置状态和 HR 实际情况。
4. **Given** 该岗位入库后，**When** 我点聊天页顶部「查看职位」打开独立职位页，**Then** 按 004 现有流程读取详情、补全信息并判断；之后回到聊天页，侧边栏显示 Jet 结论，提示语消失。
5. **Given** 当前聊天岗位已在库中（无论来源），**When** 我打开该聊天，**Then** 不覆盖库里已有的职位名、公司名等信息，不改变其判断和状态。
6. **Given** 当前聊天岗位此前只在搜索列表中出现过（已记录但没有状态、判断、HR 记录，因此不在"全部岗位"里），**When** 我打开该聊天，**Then** 该岗位从此计入"全部岗位"，已有信息保持不变。
7. **Given** 页面上读不到岗位 ID 或职位名，**When** 我打开该聊天，**Then** 不入库，侧边栏按现有规则显示读取失败或不在库提示。

---

### Edge Cases

- 快速连续切换多个聊天：每个被打开过的聊天岗位各入库一次；侧边栏只显示当前聊天的岗位（沿用 003 的防乱序规则）。
- 同一聊天反复打开：重复入库不产生重复记录，不改变已有信息。
- 聊天页读到的公司名为空：仍以岗位 ID 和职位名入库，公司名留空。
- 侧边栏改状态时，同一岗位在另一个标签页（搜索列表、岗位库）已打开：那些页面在下次刷新或重新查询时显示新状态，本期不做跨标签页即时推送。
- 列表卡片同时有 Jet 结论标识（或粗筛提示）与状态标识：两者都显示，不互相覆盖。
- 独立职位页读取失败（显示"此页暂不支持读取"）时，不做「立即沟通」自动标记（取不到可信的岗位 ID）。
- 独立职位页地址中的岗位 ID 与页面读取到的岗位 ID 不一致：不做自动标记。
- Jet 服务未运行或未配对：侧边栏状态按钮不可用并按现有规则提示连接问题；聊天岗位不入库，不重试到下次打开该聊天。

## Requirements *(mandatory)*

### Functional Requirements

**聊天页侧边栏投递状态**

- **FR-001**: 聊天页侧边栏的当前岗位卡片 MUST 显示当前聊天岗位的投递状态按钮组（收藏 / 已投递 / 不考虑），选中态与本机岗位库一致。
- **FR-002**: 用户点击按钮 MUST 通过现有投递状态保存方式修改同一份状态；点击已选中的按钮 MUST 取消状态；规则与岗位库、详情卡片一致。
- **FR-003**: 保存失败 MUST 恢复点击前的选中态并提示失败；保存期间按钮 MUST 防重复提交。
- **FR-004**: 切换聊天后，状态按钮组 MUST 随当前岗位更新，旧岗位的保存结果不得显示到新岗位上（沿用 003 防乱序规则）。

**搜索列表卡片投递状态**

- **FR-005**: 搜索列表页中有投递状态的岗位卡片 MUST 显示对应标识（"收藏""已投递""不考虑"）；没有状态的卡片 MUST NOT 显示状态标识。
- **FR-006**: 状态标识 MUST 与卡片上已有的 Jet 结论标识或粗筛提示同时可见、互不遮挡。
- **FR-007**: 在同一列表页通过右侧详情区修改状态（手动或「立即沟通」自动标记、撤销）成功后，对应卡片的状态标识 MUST 随之更新，无需刷新页面。
- **FR-008**: 状态标识 MUST 只使用列表查询时已取回的本机状态数据，MUST NOT 为显示状态额外触发判断或粗筛。

**独立职位页「立即沟通」自动标记**

- **FR-009**: 在独立职位页，用户自己点击文字恰好为"立即沟通"的按钮时，插件 MUST 把当前页面岗位状态设为"已投递"；其余规则与 002 FR-058 相同：只被动监听点击，不阻止、不改变、不代替点击；"继续沟通"等其他文字不处理；已是"已投递"时不处理；成功后显示约 8 秒可撤销提示，撤销恢复点击前状态；失败显示"未能自动标记为已投递"，不重试。
- **FR-010**: 独立职位页的岗位 ID MUST 取 004 读取到的当前页面岗位 ID，并与页面地址中的岗位 ID 核对，一致才标记；页面读取失败时 MUST NOT 标记。按钮上若带有岗位 ID 类标识，只用于核对（存在且不含该 ID 时不标记）。

**聊天岗位自动入库**

- **FR-011**: 用户在聊天页打开某会话、插件读到当前岗位 ID 和职位名后，若该岗位不在本机岗位库，插件 MUST 将其入库，只保存岗位 ID、职位名、公司名三项（公司名可为空）。
- **FR-012**: 聊天岗位入库 MUST NOT 触发规则粗筛、MUST NOT 创建判断、MUST NOT 调用 DeepSeek 或任何外部模型或服务、MUST NOT 占用每日额度、MUST NOT 设置投递状态。
- **FR-013**: 岗位已存在于本机时，聊天页入库 MUST NOT 覆盖已有的职位名、公司名及其他信息，MUST NOT 改变其判断和状态。
- **FR-014**: 在聊天页被打开过的岗位 MUST 计入岗位库"全部岗位"（在原有"有状态 ∪ 判断过 ∪ 有 HR 实际情况"之外新增"在聊天中出现过"），岗位库、聊天页侧边栏对"是否在库"的判定口径 MUST 一致。
- **FR-015**: 在库但尚未判断的岗位，侧边栏当前岗位卡片 MUST 显示职位名、公司名、投递状态按钮组、HR 实际情况编辑区，并显示提示原文："点「查看职位」获取详情并判断"。
- **FR-016**: 聊天岗位入库后，用户打开其独立职位页时 MUST 按 004 现有流程补全详情并判断；补全 MUST 可以用详情页读到的信息更新聊天页入库时保存的职位名、公司名。
- **FR-017**: 聊天页读不到岗位 ID 或职位名时 MUST NOT 入库；同一岗位重复入库 MUST NOT 产生重复记录。
- **FR-018**: 修订 003 spec：FR-059 与 User Story 9 验收场景 3 改为按本功能 FR-011–FR-015 执行，并写明修订理由（只在本机保存页面已显示的三项，发给外部的内容没有变化）；002 FR-058 与 004 FR-017 中"独立职位页暂不支持自动标已投递"的说明改为指向本功能。

**通用**

- **FR-019**: 本功能所有行为 MUST 只读取用户当前打开页面已加载的数据，MUST NOT 向 BOSS 发起任何请求、MUST NOT 自动点击、导航或改变 BOSS 上的任何状态。
- **FR-020**: 本功能 MUST NOT 改变发给 DeepSeek 或任何外部模型、服务的内容（字段、提示词均不变）。

### Key Entities

- **岗位**：本机岗位库中的岗位记录，以岗位 ID（与 BOSS 的 `encryptJobId` 一致）标识；新增"在聊天中出现过"这一事实，用于计入"全部岗位"。聊天页入库时只有岗位 ID、职位名、公司名。
- **投递状态**：用户对岗位的个人状态（收藏 / 已投递 / 不考虑 / 未设置），每个岗位一份，所有页面共用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在聊天页侧边栏修改投递状态后，刷新岗位库、打开该岗位的详情卡片，100% 显示同一新状态。
- **SC-002**: 搜索列表页中所有有投递状态的岗位卡片 100% 显示正确标识，无状态的卡片 0 个显示状态标识。
- **SC-003**: 在同一列表页修改详情区状态后，对应卡片标识在 1 秒内更新，无需刷新。
- **SC-004**: 在独立职位页点「立即沟通」，状态未设置的岗位 100% 被标记为已投递并可撤销；"继续沟通"0 次触发标记；BOSS 沟通流程 0 次被阻断。
- **SC-005**: 打开一个不在库的聊天岗位后，该岗位出现在岗位库"全部岗位"中；该过程大模型调用次数、判断记录数、每日额度使用量变化均为 0。
- **SC-006**: 打开已在库岗位的聊天后，其职位名、公司名、判断、状态 0 处被改变。
- **SC-007**: 本功能上线前后，发往外部模型的请求内容（字段集合、提示词）无差异。

## Assumptions

- 独立职位页「立即沟通」按钮的位置与文字需在实现阶段用真实页面确认；若与搜索列表页右侧详情区不同，按真实页面适配，行为规则不变。
- 聊天页读取当前岗位 ID、职位名、公司名沿用 003 现有读取方式，不新增读取范围。
- "在聊天中出现过"只在本机记录，不上传、不外发。
