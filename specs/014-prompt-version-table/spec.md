# Feature Specification: 提示词版本表 (014-prompt-version-table)

**Feature Branch**: `prompt-version-table`

**Created**: 2026-10-05

**Status**: Draft

**Input**: 2026-10-05 仓库体检报告第 15 条（「每个提示词版本在调用代码里都有一份几乎相同的分支，加一个版本要改二十多处」）。用户 2026-10-05 决定单独开一轮整理，并逐条确认了范围、验收方式和顺序（见「已定的决定」）。本 spec 只写 spec 与 tasks 两个文件。

## 背景

岗位判断的提示词从 v1 演进到 v9。每加一个版本，要逐处修改：

- `src/jet/llm/client.py` 的 `run_llm_judgement`：每个版本一段「组装消息」分支、一段「解析、结算、组装结果」分支（v9 与 v8 的两段逐行相同，只差模块名），另有一处写死的版本名单决定 `max_tokens`；
- `src/jet/worker.py`：6 处手写的版本名单，决定是否复核、是否保存事实 / 推导、是否保存 `hr_questions`、是否保存 `verdict_reason`；
- `src/jet/api/routes.py`：10 处写死的默认版本；`src/jet/domain/judgements.py`：5 处默认值和 1 个过时基线常量；`src/jet/config.py`：2 处默认值；
- 8 个旧测试文件只为改版本号而被修改。

2026-10-05 一天内 012（v8）、013（v9）两次都是这样逐处改的。漏掉 worker 名单里的一处，新版本的判断就不会被复核或会丢掉 `hr_questions`，而且不报错。另外，配置里写了不存在的版本号时，现在会悄悄按最老的 v1 判断。

## 已定的决定（2026-10-05 用户确认）

1. **范围**：只把散在各处的版本分支、版本名单、默认值收拢到一张「版本表」。v1–v9 的提示词文件全部保留、文字一个字不改，仍可用配置切换。合并或删除旧提示词文件不在本次范围。
2. **默认版本与过时基线**并排写在版本表里，是两个独立的值；每次升级时由用户决定基线提不提。
3. **配置里写了不存在的版本号**：启动时报错并列出可用版本（与其他配置项写错时的处理一致）。这是本次唯一的行为变化。
4. **先后顺序**：本轮做完、合并后，下一轮再在新结构上加 v10（销售从严只对不接受销售的用户生效），v10 只需在表里加一项。

## 要求

- **FR-001**: 版本表 MUST 是提示词版本及其能力的唯一登记处：每个版本登记它用哪个提示词模块、组装消息时需要哪些输入（从严行业、简历）、解析结果包含哪些部分（事实、推导、一句话理由、建议问 HR 的问题、简历建议）、是否做城市薪资封顶、是否支持推导截断、不开思考时的 `max_tokens`、是否参与复核。
- **FR-002**: 默认版本与过时基线 MUST 只在版本表一处定义；`config.py` 的默认值、`judgements.py` 的基线、`routes.py` 和 `judgements.py` 里的默认参数 MUST 引用它，不再出现写死的版本号。
- **FR-003**: `run_llm_judgement` MUST 只有一条组装路径和一条解析路径，由版本表驱动；`worker.py` 的 6 处版本名单 MUST 改为查询版本表的能力。
- **FR-004**: `client.py`、`worker.py`、`routes.py`、`judgements.py`、`job_status.py` 里 MUST NOT 再出现写死的版本号字面量（`"v1"`…`"v9"`）；评测里组合 A 固定用 v1 是唯一例外，改为引用版本表里的具名常量。
- **FR-005**: 层层传递却不参与判断的 `current_prompt_version` 参数（`routes.py` 10 处取值、`to_api` / `staleness` / `_job_entry` / `list_my_jobs` 等一路传递，`is_method_changed` 实际只看基线）MUST 去掉；过时判断只看版本表里的过时基线。
  - 实施时补正（2026-10-05）：这个参数并非完全没用。`request_judgement` 和 `rejudge` 新建大模型判断记录时，`prompt_version` 列写入的就是它（即配置里的版本）。因此这两个函数保留一个显式的 `prompt_version` 参数，由路由传入配置版本；其余只为向下传递而存在的参数已去掉。规则判断记录的 `prompt_version` 仍是固定的 `'rule'`，未改动。
- **FR-006**: 配置的提示词版本不在版本表里时，`load_settings` MUST 抛出 `ValueError`，消息里列出可用版本。
- **FR-007**: 发给大模型的内容 MUST 不变：对 v1–v9 每个版本，整理前后发出的消息（含 `max_tokens`、是否开启思考）和解析得到的结果、保存到数据库的判断行 MUST 逐字相同。
- **FR-008**: 以后加一个提示词版本的步骤 MUST 写在本 spec 的「加版本的步骤」一节，并且只需要：新建一个提示词模块、在版本表里加一项、决定默认版本和过时基线、写这个版本自己的测试。

## 验收标准

- **SC-001**（发出内容不变）：整理前先用一组固定的假数据（画像、岗位、2 份以上简历、勾选的从严行业）对 v1–v9 每个版本走一遍 `run_llm_judgement` 和后台判断，记录发出的请求正文、解析结果和保存的判断行，存为测试样本；整理后同一组测试逐字比对，任何一处不同即失败。这组测试留在仓库里。
- **SC-002**：服务端与插件测试全部通过；已有断言不删不放宽，确需改动的逐条说明原因。
- **SC-003**：在 `client.py`、`worker.py`、`routes.py`、`judgements.py`、`job_status.py` 里搜索版本号字面量，结果为 0。
- **SC-004**：测试里分散的「默认版本是多少」断言改为引用版本表；名字与内容不符的测试改名或补全（例如 `test_v5_judgement_not_method_changed_after_strict_industry_update` 实际没有改从严行业的步骤）。
- **SC-005**：`JET_PROMPT_VERSION=v99` 时 `load_settings` 报错，消息里列出 v1–v9。
- **SC-006**：合并到 main、重启 jet serve 之前都等用户确认。

## 加版本的步骤

1. 在 `src/jet/llm/` 新建 `prompt_vN.py`，提供组装消息与解析结果的函数（可复用上一版本）。
2. 在版本表里加一项，登记它的模块和能力。
3. 决定是否把默认版本改为 vN；单独决定是否把过时基线提到 vN（提了会让所有更早的大模型判断自动重判，花额度）。
4. 写 vN 自己的测试（提示词文字、解析、能力登记）；SC-001 的样本测试补上 vN。
5. 不需要改 `client.py`、`worker.py`、`routes.py`、`judgements.py`，也不需要改旧版本的测试。

## 不在本次范围

- 合并或删除 v1–v8 的提示词文件、删除旧版本测试。
- v10 与销售从严按画像生效（下一轮）。
- 评测、复核的其他行为改动。

## 与 constitution 的关系

- 发给外部模型的内容不变（FR-007、SC-001），不需要用户重新同意。
- 唯一的行为变化是配置写错版本号时报错（FR-006），只影响本机启动。
