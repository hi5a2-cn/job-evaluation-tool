# Feature Specification: 我的简历：上传 PDF + AI 简历画像 (009-resume-pdf)

**Feature Branch**: `009-resume-pdf`

**Created**: 2026-09-30

**Status**: Draft

**Input**: 2026-09-30 用户需求（已确认）与 Claude 定稿：
1. 设置页"我的简历"：每份改为上传 PDF（最多 3 份），简历名称默认取文件名（去掉 `.pdf`），可手动修改。
2. 上传后在本机服务端提取 PDF 文字（依赖 `pypdf 6.19.0`，纯 Python、无需编译、BSD 许可、维护活跃）。提取不到文字（扫描件）时阻断并提示"无法读取文字，请上传文字版 PDF"。
3. 提取后先在本机去掉姓名、手机号、邮箱、微信等联系方式（复用 `src/jet/llm/sanitize.py` 并增补身份证正则），再调用一次大模型生成"简历画像"（适合岗位方向 + 3～5 条核心亮点，总字数 ≤300 字）。画像在设置页展示并支持手动修改保存。调用计入 `llm_calls`，设独立每日上限，不占岗位判断每日额度。
4. 岗位判断时只发送各份简历的画像（沿用"简历1/2/3"编号和"不发简历名称"规则），绝不发简历全文。原有"适合的岗位类型"由画像取代，旧数据迁移为初始画像。
5. 本机只保存提取出的文字和画像，不保存 PDF 原文件（内存处理，不写盘、不写入数据库、不输出至日志）。删除简历时文字和画像一同删除。
6. 设置页原样更新说明文字并告知脱敏发送机制。
7. 测试全量使用虚构人物（如"李明"、13800000000、liming@example.com），严禁包含任何真实个人信息。

---

## 概述与定位

在 006 功能中，"我的简历"依赖求职者手动在设置页为每份简历编写"适合的岗位类型"（最多 200 字），存在编写成本高、提炼不专业以及无法反映简历真实技能亮点的问题。

本功能引入**上传 PDF 提取文字与 AI 简历画像提炼**：
- **上传即画像**：求职者直接上传简历 PDF 原件，系统在本机内存中完成文字解析，并自动使用大模型提炼出精炼的"简历画像"（适合方向 + 3～5 条核心亮点，≤300 字）；
- **隐私脱敏先行**：PDF 原文字在发送给大模型提炼画像前，必须先在本机剔除姓名、电话、邮箱、微信、身份证等所有联系方式与敏感身份信息；三来源确保无法识别姓名时阻断外发；
- **零 PDF 留存**：PDF 二进制流仅在内存中瞬时处理，绝不落盘存储、绝不存入数据库、绝不输出到日志；
- **判断时仅发画像**：岗位判断沿用 006 的多简历推荐机制（≥2 份有效简历时推荐最合适的一份），但上下文严格仅发送"简历1/2/3"及提炼后的 300 字画像，不发送简历全文和名称，保障 Token 经济性与隐私安全；
- **独立成本管控**：画像生成记入独立的大模型配额（`daily_resume_profile_limit`，默认每天 10 次），绝不挤占每日岗位判断额度。

### 与 Constitution 5.0.0 及主线的关系

- **原则 I（主线优先）**：服务于主线中的"按个人画像判断"环节。在候选人拥有多份简历时，通过高质量的简历画像帮助大模型精确推荐最适合该岗位的简历版本，不扩展任何自动化打招呼/投递外围功能。
- **原则 II（数据归属从第一天明确）**：简历文本、画像及配置归属于当前用户（`user_id`），保存在 `resume_slots` 表中，按用户完全隔离，其他用户无法查看，绝不写入公共岗位库。
- **原则 III（插件与本机 Jet 分离）**：插件仅负责在设置页提供文件选择、Base64 封装与画像展示交互；PDF 解析、文字脱敏与大模型提炼全部留在本机 Jet 服务端执行，两者仅通过 `127.0.0.1` 交换数据。
- **原则 IV（只读，不向招聘平台发起任何请求）**：功能仅运行于设置页与本机 Jet 之间，不向 BOSS 或任何外部招聘平台发起请求。
- **原则 VI（耗时任务后台化）**：PDF 解析与画像生成仅由用户在设置页显式点击"上传并生成画像"触发，前端异步等待，不阻塞主线浏览；打开设置页绝不自动触发大模型。
- **原则 VII（成本有上限）**：建立独立的 `daily_resume_profile_limit`（默认 10 次，0–50 可配置），独立预占与审计，不与岗位判断（`daily_llm_limit`）、沟通辅助（`daily_assist_limit`）或预判（`daily_prejudge_limit`）混用；岗位判断时仅发送 ≤300 字的画像摘要，严格控制 Token 成本。
- **原则 VIII（测试与数据安全）**：PDF 字节不落盘、不进库、不进日志；大模型外发前强脱敏；姓名三来源兜底阻断；测试夹具只用虚构人物，绝不包含真实隐私。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传 PDF 并在本机脱敏后生成简历画像 (Priority: P1) 🎯 MVP

求职者在扩展设置页的"我的简历"卡片中，点击选择本地的 PDF 简历文件。系统自动将简历名称填充为去除 `.pdf` 后缀的文件名（可手动修改）。用户可选择在"你的姓名"输入框中填入自己的姓名（仅用于本机脱敏）。点击"上传并生成画像"后，插件将 PDF 以 Base64 发送到本机 Jet。服务端在内存中提取文本，合并三来源（用户信息、输入框、PDF文本规则提取）识别姓名并进行隐私脱敏，随后调用 DeepSeek 提炼出 ≤300 字的精炼简历画像并保存入库，前端展示生成的画像文本。

**Why this priority**: 这是替换原有手填模式、实现 PDF 简历智能读取的核心 MVP 路径。

**Independent Test**: 上传一份包含虚构人物（"李明"、13800000000、liming@example.com）的文字版 PDF，系统成功提取文字并调用 MockTransport 大模型，返回结构规范的画像；断言发送给大模型的 Prompt 中不包含任何敏感联系方式；检查本地文件系统与数据库无 PDF 字节残留。

**Acceptance Scenarios**:

1. **Given** 用户选择了一个名为 `Python高级开发-张三.pdf` 的文字版简历，**When** 文件加载完成，**Then** 简历名称输入框自动填充为 `Python高级开发-张三`，用户可对其进行二次编辑。
2. **Given** 用户点击"上传并生成画像"，**When** PDF 文件大小 ≤ 5MB 且包含可提取文字（去除空白后 ≥ 50 字符），**Then** 服务端成功在内存中完成提取，调用脱敏模块过滤联系方式，调用大模型生成 ≤300 字简历画像，数据库更新对应 slot 的 `name`、`resume_text`、`profile`，并返回成功结果。
3. **Given** 用户上传了一个扫描件（图片合成的 PDF，提取文字 < 50 字符），**When** 服务端检测到有效文字不足，**Then** 拒绝调用大模型，返回 422 状态码与错误信息 `{error: "no_text", message: "无法读取文字，请上传文字版 PDF"}`，数据库保持原样。
4. **Given** 用户上传了加密或损坏的 PDF，**When** 服务端尝试解析，**Then** 返回 422 状态码与明确错误提示 `{error: "pdf_invalid", message: "PDF 文件已加密或已损坏，无法解析"}`。
5. **Given** 用户上传了超过 5MB 的文件，**When** 请求到达，**Then** 返回 413/422 错误提示文件过大。

### User Story 2 - 姓名识别多源融合与强脱敏安全阻断 (Priority: P1)

为了保障绝对不向第三方大模型泄露求职者真实身份，系统从三个来源提取姓名进行交叉脱敏：1) `users.display_name`；2) 上传 / 重新生成请求中的 `self_name`；3) PDF 文字模式识别（`姓名[:：]\s*(\S{2,4})`，或首行 2–4 汉字/首字母大写英文名）。三者去重合并后构造脱敏敏感词表。**确认来源**只有前两个：两者都没有时一律阻断大模型调用；PDF 里识别出的姓名只作为额外脱敏词，不能单独让检查通过（2026-10-06 体检第 58 条按实现修订）。

**Why this priority**: 核心安全底线（原则 VIII），防止任何形式的个人敏感数据外泄。

**Independent Test**: 构造三份测试数据：1) 仅 PDF 含姓名；2) 请求参数含 `self_name`；3) 全无姓名。只有第 2 份能脱敏并外发；第 1、3 份立即拦截并返回 422 `self_name_required`（2026-10-06 体检第 58 条按实现修订）。

**Acceptance Scenarios**:

1. **Given** 用户在上传区填写了 `李四`，且 PDF 文本首行包含 `李四` 或文本包含 `姓名：李四`，**When** 执行脱敏，**Then** 自动生成尊称组合（如 `李先生`、`李女士`），正文中出现的姓名被彻底替换为 `[已隐藏]`；若用户没有填写姓名（数据库也无 `display_name`），即使 PDF 能识别出姓名也返回 422 `self_name_required`，不调用大模型（2026-10-06 体检第 58 条按实现修订）。
2. **Given** PDF 文本结构复杂无法正则匹配姓名，但用户在上传区输入了 `王五`，**When** 执行脱敏，**Then** 成功将正文中的 `王五` 脱敏。
3. **Given** 用户没有填写姓名且数据库无 `display_name`，**When** 尝试生成画像，**Then** 服务端阻断大模型请求，返回 422 状态码 `{error: "self_name_required", message: "没有识别出你的姓名，请在上传区填写姓名后重试（只在本机用于去掉姓名）"}`，不扣除额度，不调用大模型。
4. **Given** 简历中包含 18 位身份证号码、手机号、邮箱、微信 ID，**When** 文本经过脱敏，**Then** 所有这些敏感信息 100% 被替换为占位符 `[已隐藏]`，外发请求体验证无残留。

### User Story 3 - 岗位判断时只发送简历画像 (Priority: P1)

当用户浏览岗位详情触发判断时，系统读取用户当前已配置的简历。若有效简历 ≥ 2 份，提示词追加简历推荐指令。与旧版发送"适合的岗位类型"不同，本功能将提示词段落升级为 `- 简历{slot}：{profile}`。判断提示词中绝对不发送简历名称、不发送简历原文字全文，仅发送编号与 300 字画像。模型给出的推荐结果解析后在卡片中正常呈现。保持 `prompt_version = "v6"` 不变，防止历史已判断岗位失效。

**Why this priority**: 这是简历画像在核心主线中的消费端，确保模型推荐具备充足依据且不膨胀上下文。

**Independent Test**: 配置 2 份具有画像的简历，触发岗位判断并捕获发送给 DeepSeek 的 messages，断言包含 `- 简历1：...`，断言不包含简历原始文本、不包含简历名称，断言 `prompt_version` 维持 `v6`。

**Acceptance Scenarios**:

1. **Given** 用户录入了 2 份简历，分别带有提炼后的画像，**When** 触发岗位判断，**Then** 提示词中的简历信息格式为 `- 简历1：<画像1>` 与 `- 简历2：<画像2>`，模型据此给出最匹配的简历编号与 ≤40 字推荐理由。
2. **Given** 用户仅有 1 份简历或 0 份简历，**When** 触发岗位判断，**Then** 不在提示词中附加简历建议段落。
3. **Given** 系统升级至本功能，**When** 用户查看历史已判断的岗位卡片，**Then** 历史判断不被标记为过时（stale=false），维持原有结论呈现。

### User Story 4 - 简历画像编辑、重新生成与删除清理 (Priority: P2)

用户在设置页查看已生成的简历画像，可随时在文本框中手动微调（实时展示字数，≤300 字限制），并点击"保存修改"保存。若用户调整了简历原文字脱敏规则或希望重新生成，可点击"重新生成画像"（复用已保存的 `resume_text` 重新脱敏并调用大模型）。用户点击"删除"时，服务端物理删除该 slot 记录，清空数据库中的名称、提取文字与画像，彻底清理所有痕迹。

**Why this priority**: 赋予求职者充分的控制权与纠偏能力，保障个人数据生命周期完整闭环。

**Independent Test**: 对指定 slot 执行编辑保存、重新生成与删除操作，验证数据更新正确，删除后数据库该行彻底清除。

**Acceptance Scenarios**:

1. **Given** 用户对自动生成的画像不完全满意，**When** 在文本框中编辑内容并点击"保存修改"，**Then** 服务端保存更新后的 `name` 与 `profile`，保留原本提取的 `resume_text`，不触发大模型调用。
2. **Given** 用户希望重新生成画像，**When** 点击"重新生成"，**Then** 服务端读取已存储的 `resume_text`，重新脱敏并预占额度后调用大模型，生成新画像并更新数据库。
3. **Given** 用户点击某份简历的"删除"按钮并确认，**When** 请求完成，**Then** 数据库该 slot 整行删除，名称、提取文字、画像彻底销毁；设置页恢复为空位状态。

---

### User Story 5 - 独立配额与额度耗尽降级处理 (Priority: P2)

简历画像生成设有独立的每日配额（`daily_resume_profile_limit`，默认每天 10 次，0–50 可配置）。该额度与正式判断、沟通辅助、列表预判额度完全独立。当今日画像生成额度耗尽或未配置 API Key 时，上传请求仍将提取的 `name` 和 `resume_text` 保存到该 slot，但画像字段留空或保留旧值，服务端返回明确的提示状态码（429 `quota_exhausted` 或 409 `no_llm_key`），前端提示用户稍后重试或配置 Key。

**Why this priority**: 遵循原则 VII，防止偶发的大量简历上传消耗常规求职判断的额度。

**Independent Test**: 将配额耗尽后触发上传，断言返回 429 且 `resume_text` 已安全保存入库。

**Acceptance Scenarios**:

1. **Given** 今日画像生成调用次数已达到 `daily_resume_profile_limit`，**When** 用户上传新简历，**Then** 服务端提取文字并保存 `resume_text` 与 `name`，拦截大模型调用，返回 429 状态码与提示信息，前端显示"今日生成画像次数已达上限，文字已保存，请明天重试或手动填写画像"。
2. **Given** 用户尚未配置 DeepSeek API Key，**When** 上传简历，**Then** 服务端提取文字并保存 `resume_text` 与 `name`，返回 409 状态码，前端提示"已保存简历文字，配置 API Key 后可生成画像"。

### Edge Cases

- **纯图片扫描件 PDF**：`pypdf` 提取出的字符串去除所有空白后长度 $< 50$，服务端统一判定为扫描件，返回 422 `no_text`，明确提示"无法读取文字，请上传文字版 PDF"。
- **加密或损坏 PDF**：捕获 `pypdf.errors.PdfReadError`，返回 422 `pdf_invalid`，明确提示已损坏或被密码保护。
- **超大 PDF 文件（> 5MB）**：前端选文件时与服务端接口校验，拦截超过 5MB 的文件，返回 413/422。
- **大模型响应超长或格式畸变**：模型生成的画像文本若超过 300 字，服务端进行安全截断或清理；若生成内容为空，返回错误并保留原提取文字。
- **历史 v8 数据平滑升级**：从 v8 升级至 v9 时，旧 `resume_slots` 中的 `job_types` 迁移为 `profile`，`resume_text` 置为 `NULL`，既有简历配置不丢失。
- **并发重复上传同一 Slot**：SQLite 事务采用 `BEGIN IMMEDIATE`，同一用户同一 slot 的更新操作原子覆盖。

## Requirements *(mandatory)*

### Functional Requirements

#### 数据库与迁移模型 (v9)

- **FR-001**: 数据库迁移 v9 MUST 重建 `resume_slots` 表，结构包含：
  `user_id TEXT NOT NULL`, `slot INTEGER NOT NULL CHECK(slot IN (1, 2, 3))`, `name TEXT NOT NULL CHECK(length(name) <= 100)`, `resume_text TEXT`, `profile TEXT NOT NULL CHECK(length(profile) <= 300)`, `updated_at TEXT NOT NULL`, `PRIMARY KEY(user_id, slot)`，并保持外键约束引用 `users(id)`。
- **FR-002**: 迁移 v9 MUST 将旧表中的 `job_types` 字段迁移至新表的 `profile` 字段，旧记录的 `resume_text` 置为 `NULL`；完整保留所有历史简历记录。
- **FR-003**: `llm_calls.purpose` 的 CHECK 约束 MUST 扩展加入 `'resume_profile'`，迁移过程 MUST 通过重建表方式完整保留现有历史记录。
- **FR-004**: `user_settings` 表 MUST 新增列 `daily_resume_profile_limit INTEGER NOT NULL DEFAULT 10 CHECK(daily_resume_profile_limit BETWEEN 0 AND 50)`；额度在 `jet.llm.quota` 中由 `purpose='resume_profile'` 独立管理，MUST NOT 与正式判断、沟通辅助或列表预判配额混用。

#### PDF 提取与敏感信息脱敏

- **FR-005**: 服务端 MUST 使用纯 Python 库 `pypdf`（6.19.0）在内存中解析 PDF Base64 流，严禁将 PDF 原文件或二进制写入磁盘、数据库或日志中。
- **FR-006**: 若 PDF 去除空白后的文本长度 $< 50$ 字符，服务端 MUST 拒绝调用大模型，并返回 422 错误 `{error: "no_text", message: "无法读取文字，请上传文字版 PDF"}`。
- **FR-007**: 服务端脱敏模块 MUST 融合三个姓名来源（`users.display_name`、上传请求中的 `self_name`、从 PDF 文本提取的姓名正则与首行规则），去重合并后调用 `get_sensitive_name_terms`；其中只有前两个是确认来源，PDF 识别出的姓名只作补充（2026-10-06 体检第 58 条按实现修订）。
- **FR-008**: 若两个确认来源（`self_name`、非占位的 `users.display_name`）都没有姓名，服务端 MUST 拒绝调用大模型，并返回 422 错误 `{error: "self_name_required", message: "没有识别出你的姓名，请在上传区填写姓名后重试（只在本机用于去掉姓名）"}`。
- **FR-009**: `sanitize.py` 中的 `sanitize_text` MUST 增补 18 位中国居民身份证号码正则过滤，将身份证号、手机号、邮箱、微信及识别出的姓名全部替换为 `[已隐藏]`。

#### 服务端 API 与画像生成

- **FR-010**: 服务端 MUST 提供 `POST /v1/resumes/upload` 接口（需配对鉴权），接收 `{slot, name, pdf_base64, self_name}`（不含原始文件名，体检第 79 条）。执行流程：
  1. 校验 PDF 大小 ≤ 5MB；
  2. 内存提取文字并校验有效字数 ≥ 50；
  3. 执行隐私脱敏；
  4. 预占配额（`purpose='resume_profile'`）；
  5. 若额度耗尽、未配 Key 或画像生成失败，保存 `name` 与 `resume_text`；该 slot 原来保存的是同一份简历正文时保留旧 `profile`，换了另一份简历或原来没有时 `profile` 置空（画像为空的简历不参与判断，点「重新生成画像」后补上），返回对应状态并带上当前 `profile`（2026-10-05 体检第 29 条修订）；
  6. 调用大模型提炼画像，校验输出 ≤300 字；
  7. 原子保存该 slot 的 `name`、`resume_text`、`profile` 与 `updated_at`；
  8. 返回 `{slot, name, profile, text_chars}`。
- **FR-011**: 服务端 MUST 提供 `POST /v1/resumes/{slot}/regenerate` 接口，利用库内已保存的 `resume_text` 重新脱敏、预占额度并生成画像。
- **FR-012**: 服务端 MUST 更新 `GET /v1/resumes` 接口，返回列表包含 `[{slot, name, profile, has_text, text_chars, updated_at}]`，MUST NOT 返回 `resume_text` 全文。
- **FR-013**: 服务端 MUST 更新 `PUT /v1/resumes` 接口，支持保存用户对名称和画像的手动修改（`profile` ≤ 300 字且非空），保持 `resume_text` 不变。
- **FR-014**: 服务端 MUST 提供 `DELETE /v1/resumes/{slot}` 接口，彻底删除该 slot 的数据行（名称、提取文字、画像物理删除）。
- **FR-015**: 提示词模块 `src/jet/llm/resume_profile.py` MUST 仅向大模型发送脱敏后的简历正文及生成指令，严禁发送简历名称、文件名、用户 ID 等任何多余数据；严禁在日志中记录完整提示词或大模型输出全文。

### Key Entities

- **ResumeSlot（简历槽位实体）**：用户个人数据实体，存储槽位编号（1–3）、自定义名称（≤100字）、提取出的脱敏源文字（`resume_text`，可空）、AI 提炼或手动修改的画像（`profile`，≤300字）以及更新时间。
- **ResumeProfilePrompt（画像生成提示词）**：包含系统角色设定与精简生成指令的轻量模型输入结构，输入仅包含脱敏后的简历文本，要求输出适合方向与 3～5 条亮点。
- **ResumeQuota（画像生成配额）**：以 `purpose='resume_profile'` 记录于 `llm_calls` 的独立调用配额模型，每日限额 `daily_resume_profile_limit`（默认 10）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 文字版 PDF 上传后，系统在 5 秒内完成文字提取、本地脱敏、模型调用并回显 ≤300 字的结构化画像。
- **SC-002**: 提取文字在发送给大模型前，姓名、手机号、邮箱、微信、18 位身份证号码的识别与掩码脱敏率达到 100%（基于虚构测试集断言）。
- **SC-003**: 无论上传成功、失败或异常，系统本地数据目录下的 `.pdf` 文件留存数严格为 0，数据库中的二进制字节数严格为 0。
- **SC-004**: 在三来源均无姓名的情况下，大模型调用拦截率达到 100%，无任何请求外发。
- **SC-005**: 岗位判断提示词中的简历上下文 100% 仅包含画像内容与简历编号，简历名称与简历原文字全文的外发次数严格为 0。
- **SC-006**: 升级后 `prompt_version` 维持 `v6`，既有岗位的判断结论 100% 保持有效且无额外重判开销。
- **SC-007**: 简历画像生成调用的账单消耗独立记录，岗位判断每日额度（`daily_llm_limit`）消耗数严格为 0。

## Assumptions & 边界约束

- **模型依赖**：简历画像生成调用非思考模型（`judge_engine`，默认 `deepseek-flash:no-think`），生成耗时通常在 2 秒以内。
- **PDF 格式边界**：仅支持标准 PDF 文字版（Text-based PDF）。扫描件、纯图片 PDF、被加密且无密码的 PDF 不在识别支持范围内，系统进行友好的错误拦截与提示。
- **单用户环境**：第一阶段支持单机单用户使用，架构设计已按 `user_id` 严格隔离支持多用户扩展。
- **范围外**：
  - OCR 图片识别转换；
  - 自动向招聘平台上传或投递 PDF 原件；
  - Word（`.docx`）或 Markdown 等其他文件格式的解析。
